## Release process (established this session)

Direct commits to `main`, no PR workflow (solo-maintainer repo). Pattern, from git log:
1. One commit per feature/fix, each adding its own CHANGELOG.md bullet under the version-in-progress heading (create the heading with the first bullet of a new version).
2. A final `chore(release): vX.Y.Z` commit that *only* bumps `package.json` + `package-lock.json` (via `npm version X.Y.Z --no-git-tag-version`) — no CHANGELOG touch, that already happened in the feature commits.
3. `git tag vX.Y.Z && git push origin main && git push origin vX.Y.Z`. The tag push triggers `.github/workflows/release.yml` (`grafana/plugin-actions/build-plugin`), which builds and publishes the actual release artifact.
4. CI's e2e job (`appConfig.spec.ts`, `appNavigation.spec.ts`) fails on every Grafana version tested, including on `main` before any of this session's changes — pre-existing/unrelated, not something introduced here. The `Release` workflow itself (which is what actually matters for shipping) has been passing.

## Naming convention (use this when talking about pages)

- A top-level list page is named plainly: **Clusters**, **Nodes**, **Namespaces**, **Workloads**, **Alerts**.
- Its detail/drilldown page (reached by clicking a row) is named "**\<Name\> Drilldown**", e.g. **Clusters Drilldown**.
- This is also saved in persistent memory (`feedback_page_naming.md`).

## What exists today

### Clusters (list page) — `src/scenes/clustersApp.tsx: getClustersListScene`
Table of all clusters (Cluster/Nodes/Alerts/CPU Avg/Avg%/Max/Max%/Mem Avg/Avg%/Max/Max%). Cluster column links to **Clusters Drilldown**; Nodes column links to **Nodes** page; Alerts column links to the **Alerts** page (`?var-cluster=<cluster>`, per-row, native table link). Thresholds: orange <60%, green 60–90%, red >90% (`usageThresholds`, redeclared per-file — no shared module for it). All table columns are left-aligned.

### Clusters Drilldown — `getClusterDetailPage` in clustersApp.tsx
Tabbed page: **Overview, CPU, Memory, Network, Storage**. Title renders as "\<cluster-name\> [cluster]" badge via `ClusterPageTitle`. Datasource picker + timepicker in page-level controls. (Unchanged this session — see git history/earlier summaries for the CPU/Memory/Network/Storage tab internals if picking this back up.)

### Nodes (list page) — `src/pages/Nodes/nodesPage.tsx` + `src/queries/nodeQueries.ts`
Table across all selected clusters: Cluster/Node/Alerts/CPU Avg/Avg%/Max/Max%/Mem Avg/Avg%/Max/Max%. Same thresholds/colored-icon-cell style as Clusters. Cluster column → Clusters Drilldown; Alerts column → Alerts page (pre-filtered by cluster+node). Joined with `joinByField(byField: 'node', mode: 'outer')` — every query except `info` drops `cluster` from its outermost grouping (kept only via `info`) to avoid duplicate "Cluster" columns after the join, since `joinByField` doesn't disambiguate identically-named non-value fields across queries. This works here because node names are unique across clusters in practice.

### Namespaces (list page) — `src/pages/Namespaces/namespacesPage.tsx` + `src/queries/namespaceQueries.ts`
Table across all selected clusters: Cluster/Namespace/Workloads/Alerts/CPU Usage/Requests/Requests%/Mem Usage/Requests/Requests%/Limits/Limits%. **Uses Grafana's `merge` transform, not `joinByField`** — this was a bug fix mid-session (see gotcha below): an earlier `joinByField`-based version trimmed `cluster` down to only the `info` query (mirroring the Nodes approach), which meant the whole Cluster column's presence depended on that one query returning data. On this demo dataset `info`'s underlying metrics (`kube_pod_owner`, `kube_namespace_status_phase`) happened to be sparse, so the Cluster column (and most rows) silently vanished, leaving only the 3 columns backed by queries that *did* have data. Fixed by restoring every query's original `by (cluster, namespace)` grouping verbatim and switching to `{ id: 'merge', options: {} }`, which matches rows by every field name common to all queries instead of one join key — no single query is a single point of failure for the identity columns.

### Workloads (list page) — `src/pages/Workloads/workloadsPage.tsx` + `src/queries/workloadQueries.ts`
Table across all selected clusters/namespaces: Cluster/Namespace/Workload/Type/**Pods**/CPU Usage/Requests/Requests%/Mem Usage/Requests/Requests%/Limits/Limits%. A workload's identity is `(cluster, namespace, workload, workload_type)` — genuinely multi-dimensional, since workload names repeat across namespaces/clusters (e.g. an "api" Deployment in many namespaces) — so this **also uses `merge`**, and every one of its 10 queries keeps its full original grouping verbatim; no trimming was needed or attempted here (unlike Nodes/Namespaces).

**Pods column** (`readyDesiredPodsCell` in `tableCells.tsx`) shows `ready / desired` text over a proportional colored bar (green once ready catches up to desired, red while short), matching Grafana Play's combined column instead of two separate "Ready Pods"/"Desired Pods" columns. Implementation notes for next time:
- Built as a small hand-rolled `<div>`+`<span>` (bar = absolutely-positioned colored div sized by `%`, text centered on top), **not** `@grafana/ui`'s `BarGauge` component — `BarGauge`'s color logic (`getCellColor`) needs a real `DisplayProcessor` function wired to thresholds, which isn't something a `CustomCellRendererProps`-based cell gets for free, and this couldn't be visually verified without a browser. The hand-rolled version matches the rest of this codebase's existing style (`UsageIcon`, `ResourceUsageLegend` are also plain divs/spans) and its behavior is fully inspectable from the code alone.
- The `Value #desired_pods` field must stay **present in the data** (the cell reads it via `findFraction` for the same row) but **hidden as its own column** via `overrideCustomFieldConfig('hideFrom', { viz: true, legend: false, tooltip: false })` on that field. This is different from `organize`'s `excludeByName`, which would remove the field from the frame entirely and break the lookup — confirmed by reading `@grafana/ui`'s `Table/utils.mjs`, which skips rendering a column when `field.config.custom.hideFrom?.viz` is set but doesn't touch the underlying frame.
- Readiness coloring is **inverted** from this codebase's usual usage-tier scale (low=orange/underused, high=red/near-capacity elsewhere) — here more-ready-than-desired is good (green), less is bad (red), so it doesn't reuse `usageTierFromFraction`.

**No `workload` filter variable on this page**: the old stub had one, but none of the given queries filter by `$workload`, and wiring a client-side row filter to it would need unverified Scenes variable-interpolation inside a transform's `options` (untested, so left out rather than half-implemented). Revisit if asked.

**Multi-cluster gotcha inherited from the given queries (real, not just a demo issue)**: the cpu/mem queries join via `* on(namespace, pod) group_left(workload, workload_type) namespace_workload_pod:kube_pod_owner:relabel{...}` — note `cluster` is *not* in the `on(...)` clause. If the **same pod name** exists in the same namespace on two *different* selected clusters (e.g. every cluster's first StatefulSet replica named `app-0`), Prometheus errors the whole query with `"many-to-many matching not allowed"` — not silently wrong data, a hard failure, and it kills the entire column for every workload, not just the colliding one. This is a property of the official queries as given (translated literally, not "fixed" per the usual rule), so it will bite in a real cluster too if pod-naming conventions collide across clusters. Worth flagging to the user if it comes up again; the fix (if ever wanted) would be adding `cluster` to the `on(...)` clause, which changes the query's semantics from what was given.

### Alerts (top-level page) — `src/pages/Alerts/alertsPage.ts` + `investigateActionCell.tsx`
Kubernetes-icon + "Alerts" title, datasource picker + `cluster`/`node`/`namespace`/`severity`/`alertname` variable pickers + timepicker. 3 timeseries panels + a table with a synthetic **Action** column driving an `OpenAssistantButton` ("Investigate").

**Two classes of bugs found and fixed this session, both worth remembering:**

1. **Empty alert details in the Investigate prompt** — `investigateActionCell.tsx` looked up field values by the table's ALL-CAPS *display* names (`CLUSTER`, `SEVERITY`, ...). Grafana's `organize` transform's `renameByName` only sets `field.config.displayName`/`field.state.displayName` — it does **not** rename the underlying `field.name`. Fixed by reading the original lowercase field names instead. **General lesson: never look up a field by a name that only exists after a `renameByName` — always use the pre-rename name.**
2. **The sidebar opened but the prompt never appeared/sent** — this was in the org's Assistant fork, `grafana-pi-app`, not in this plugin. See below.

**The user's org runs a custom, in-house-forked assistant app** (https://github.com/elohmeier/grafana-pi-app, default plugin id `g42-pi-app`), shipping an alternate `grafana-assistant-app`-ID build as a drop-in for the official `@grafana/assistant` npm package. Three upstream bugs found and fixed there across sessions, **all in `Lprod`'s fork** (`https://github.com/Lprod/grafana-pi-app`, synced from upstream via `gh repo sync`), PR'd against `elohmeier/grafana-pi-app`:

1. **PR [#30](https://github.com/elohmeier/grafana-pi-app/pull/30)** (merged, v2.18.1): `ASSISTANT_SIDEBAR_TITLE` hardcoded to `'Assistant'` even in the `grafana-assistant-app` build, but `@grafana/assistant`'s `isAssistantAvailable()` requires an exact match against `'Grafana Assistant'` — `OpenAssistantButton` always resolved `isAvailable: false`. Fixed: conditional on `pluginJson.id === ASSISTANT_PLUGIN_ID`.
2. **PR [#31](https://github.com/elohmeier/grafana-pi-app/pull/31)** (merged): a second, independent hardcoded `'Assistant'` in `scripts/package-plugin-variant.mjs`'s static manifest baking — fixing #30 alone made the button *visible* but clicking it did nothing, since Grafana core resolves the `OpenExtensionSidebarEvent` target from the static manifest too.
3. **PR [#32](https://github.com/elohmeier/grafana-pi-app/pull/32)** (open, this session): `openAssistant()`/`<OpenAssistantButton>` sends `initialPrompt`/`initialContext`/`initialAutoSend`/`chatId`/`appendContext` via the `open-extension-sidebar` event, but the registered `AssistantSidebar` component only ever accepted `action`/`agentWorkspaceLaunch`/`contextId`/`path`/`sessionId` — those five props were silently dropped, so the sidebar opened with an *empty* chat regardless of what a third-party plugin passed. Separately, **no launch path in that app ever auto-submitted a prompt** — every existing one (dashboard-panel-menu actions, agent-workspace launch) only pre-fills the input via `setInput(...)`; `@grafana/assistant`'s contract defaults `autoSend` to `true`, so a real auto-submit path (`submitPromptText`, extracted from `submitPrompt`) was new, not just a plumbing fix. Verified locally end-to-end: patched the built `grafana-assistant-app` bundle in place (frontend-only `npm run build:variant`, kept the existing release's backend binaries — a from-source build produces no backend executable and Grafana refuses to load the plugin without one) inside the container currently swapped in for the official Assistant (see below), clicked "Investigate" on a real alert, confirmed the prompt appeared and was sent automatically with real field values. 256/256 tests passing (249 pre-existing + 7 new for the new pure helpers).

**If a future session hears "the Investigate button doesn't work" again**, check in order: (a) which plugin id is installed (`g42-pi-app` vs `grafana-assistant-app`), (b) whether the deployed `grafana-pi-app` version includes all three fixes above, (c) whether `extensionSidebar` feature toggle is enabled, (d) whether the alert *fields themselves* are populated in the prompt (a `renameByName`-vs-`field.name` bug like #1 above) as distinct from whether the sidebar/prompt mechanism fires at all (bugs #2/#3) — these are independent failure modes, check both.

## Known gotchas discovered this/previous sessions (read before repeating work)

1. **Grafana's `renameByName` (in the `organize` transform) only sets a field's display name, never its underlying `field.name`.** Any custom cell renderer or code that looks up `frame.fields.find(f => f.name === X)` must use the pre-rename name, not whatever `renameByName` maps it to. Bit the Alerts "Investigate" button this session (looked up `'CLUSTER'` when the real name was `'cluster'`).
2. **`joinByField` is only safe when the join key is a single field that's actually unique across everything being combined.** It silently drops the whole column for any field not carried by the query you happen to designate as that field's sole source — trimming other queries' groupings to avoid duplicate columns (as done for Nodes) creates a single point of failure if that one query returns sparse/no data (bit Namespaces this session). **When the natural identity is multi-field (Namespaces: cluster+namespace; Workloads: cluster+namespace+workload+workload_type), use Grafana's `{ id: 'merge', options: {} }` transform instead** — it matches rows by every field name common to all queries in the pipeline, not one designated join key, and doesn't have either failure mode.
3. **Cross-page filter variable propagation — the full, correct story.** `SceneAppPage`'s `$variables` are constructed **eagerly** for **every** top-level page at once, the instant `getClustersSceneApp()` runs. Since every top-level page independently declares its own same-named `cluster`/`namespace`/etc variable, Scenes' URL-key deduplication silently renames every page but the first-registered one, and a cross-page link's plain `var-cluster=...` lands on a suffixed key nothing reads. Fixed in `datasourceVariables.ts`:
   - Each filter variable re-syncs its value from the raw URL query param **on activation** (`addActivationHandler` + `changeValueTo`), never from the constructor.
   - Filter variables are excluded from every top-level page's `preserveUrlKeys` (kept only `from`/`to`/`timezone`/`refresh`/`var-datasource`).
   - **Do not reintroduce a constructor-time URL read, and do not add filter variable names back to `preserveUrlKeys`.**
4. **`plugin.json` changes need a full Grafana container recreate**, not just a rebuild/restart. Pure code/panel changes only need `podman restart`.
5. **Webpack build cache goes stale** with the `node_modules`-symlink shortcut — `rm -rf node_modules/.cache/webpack` before trusting a build.
6. **Local demo containers (`kube-metrics-demo`, `prometheus`, `debeka-k8s-app` Grafana) bind-mount files from whatever worktree last recreated them, not necessarily this one.** `podman inspect <container> --format '{{range .Mounts}}...'` before assuming a container is serving *this* worktree's files — recreate with an explicit `podman run -v <this-worktree-absolute-path>/...` if it's pointed elsewhere. Recreate, don't just restart, after editing a bind-mounted file (restart alone re-uses the same already-resolved mount but the *process* inside still needs to notice the change — for the metrics/prometheus.yml files this means recreate; for the Grafana plugin's `dist/`, a `podman restart` is enough once the mount source is already correct).
7. **Adding a genuinely new npm dependency requires a real `npm install`, not the symlink trick.**
8. **`joinByField` needs `mode: 'inner'`, not the default `'outer'`, when one of the joined queries is meant to act as an allow-list filter.**
9. **Grafana's built-in reducer/calc ids often already say exactly what's needed, verbatim** — `p95` → `"95th %"`, `lastNotNull` → `"Last *"`. Check `@grafana/data`'s `fieldReducer.mjs` for the exact id before inventing a custom label.
10. **A flexbox `SceneFlexItem` with `xSizing: 'fill'` plus `minWidth: 0` still won't guarantee equal-width siblings if one contains a long unbroken string** — set an explicit `width: '50%'` on both items instead of relying on flex distribution.
11. **This local Prometheus's `kube-metrics-demo` scrape job needs `honor_labels: true`.** Several demo metrics embed their own `job` label (e.g. `kube_pod_container_resource_requests{job="kube-state-metrics",...}`, matching what the real Namespaces/Workloads queries filter on) — without `honor_labels`, Prometheus overwrites that with the scrape job's own name (`kube-metrics-demo`), moving the original value to `exported_job`, so `job="kube-state-metrics"` filters would never match anything. Set in `demo/prometheus/prometheus.yml`. (Real kube-state-metrics scrape configs commonly set this for the same reason, so this isn't a demo-only hack.)
12. **A `Nodes: Standalone plugin pages` Helm config option can hide specific app pages from the Grafana nav without touching plugin code**, discussed this session for hiding not-yet-finished pages before a prod trial:
    ```yaml
    grafana:
      grafana.ini:
        navigation.app_standalone_pages:
          /a/debeka-k8s-app/namespaces: hidden-kubernetes-pages
    ```
    Verified directly against Grafana core source (`pkg/services/navtree/navtreeimpl/applinks.go`): any path listed here is *unconditionally* removed from the plugin's own nav section; it only gets re-attached elsewhere if the given value matches a *real* nav section ID (`treeRoot.FindById(...)`). An arbitrary/nonexistent value like `hidden-kubernetes-pages` means it's removed and never re-attached — fully hidden. This is nav-tree cosmetics only, not access control — the page is still reachable by direct URL. Needs a Grafana restart (config is read once in `readNavigationSettings()` at boot), which Helm upgrades typically trigger automatically via the changed ConfigMap/Secret.

## Demo data (`demo/kube-metrics/metrics` + `demo/prometheus/prometheus.yml`)
Has: node info/capacity, per-node CPU/memory recording-rule-style aggregates, namespace-level CPU/memory recording-rule-style sums, a full set of storage metrics (PVC/PV/kubelet_volume_stats/container_fs_*), enriched `ALERTS`, and (added this session) a small **Workloads demo set** in namespace `default` on both clusters: a Deployment "app" (reusing the pre-existing `app-0` pod for Storage/Alerts purposes, but a *separate* cluster-suffixed pod identity — `app-aws`/`app-gce` — for the new workload-attribution/resource-request/usage metrics, to avoid a cross-cluster pod-name collision, see below), a DaemonSet "node-agent", a StatefulSet "cache", a completed Job "db-migrate", and a bare pod "debug-shell" — one of each `workload_type` the Workloads page's queries recognize except `replicaset`/`staticpod` (deliberately skipped as redundant edge cases).

**Two non-obvious things about this new data:**
- **All new/synthetic pod names are cluster-suffixed** (`node-agent-0-aws`/`node-agent-0-gce`, etc.) specifically to avoid the multi-cluster `on(namespace, pod)` collision described in the Workloads gotcha above — if you add more synthetic workloads, keep pod names cluster-unique or the whole Workloads cpu/mem query set will hard-error again.
- **Deliberately did NOT add pod-level rows to `node_namespace_pod_container:container_cpu_usage_seconds_total:sum_irate`** — that metric already exists at *node* granularity and is summed by the Cluster CPU chart and the Namespaces page's CPU Usage column; adding pod-level rows under the same name would double-count into those already-correct totals. As a result, Workloads' **CPU Usage** and **CPU Requests %** columns stay empty in the demo (everything else — Ready/Desired Pods, CPU Requests, all Mem columns — populates correctly). This is a demo-data-only gap; a real cluster's kube-state-metrics/cAdvisor naturally carries a `pod` label on the equivalent real metric.

`container_fs_{reads,writes}_total` counters are static in the demo file, so `rate()` on them evaluates to 0 — the Storage tab's Throughput/IOPS panels showing a flat 0 line is expected, not a bug.

# Session Summary — debeka-k8s-app (Grafana K8s Observability App Plugin)

**Repo:** https://github.com/Lprod/grafana-k8s-app (branch `main`)
**Current release:** `v1.1.1` on GitHub; this session's work is being released as **`v1.2.0`** (tag/release created right after this file was written — check GitHub if you need to confirm it landed).
**Reference design:** https://play.grafana.org/a/grafana-k8s-app/navigation/cluster/... ("Grafana Play") — this plugin is being rebuilt to visually/functionally match Grafana's own official Kubernetes Monitoring app, tab by tab. The user pastes the exact PromQL + panel titles from Grafana Play for each tab; translate `$cluster`/`$namespaces`/`$nodes` literally into this codebase's variable-interpolation style (see existing tabs for the pattern) rather than "fixing" them to look more consistent — the user has occasionally used different filter operators (`=` vs `=~`) or omitted a variable filter on purpose between panels, and that's preserved intentionally.

## Naming convention (use this when talking about pages)

- A top-level list page is named plainly: **Clusters**, **Nodes**, **Namespaces**, **Workloads**, **Alerts**.
- Its detail/drilldown page (reached by clicking a row) is named "**\<Name\> Drilldown**", e.g. **Clusters Drilldown**.
- This is also saved in persistent memory (`feedback_page_naming.md`).

### Alerts (new top-level page) — `src/pages/Alerts/alertsPage.ts` + `investigateActionCell.tsx`
Built from scratch this session, registered in `plugin.json` includes and `getClustersSceneApp()`'s `pages` array (`ROUTES.Alerts = 'alerts'`). Kubernetes-icon + "Alerts" title, datasource picker + `cluster`/`node`/`namespace`/`severity`/`alertname` variable pickers (all new — `SEVERITY_VARIABLE_NAME`/`ALERTNAME_VARIABLE_NAME` + `createSeverityFilterVariable`/`createAlertnameFilterVariable` added to `datasourceVariables.ts`) + timepicker. 3 timeseries panels (Firing alerts by cluster/by namespace, Alert severity) + a table titled `Firing Alerts at ${__to:date:YYYY-MM-DD HH-mm-ss}` (Grafana's built-in `$__to` macro, interpolated live) with columns CLUSTER/SEVERITY/ALERTNAME/NAMESPACE/POD/CONTAINER/ENDPOINT/INSTANCE/JOB (built via `filterFieldsByName` whitelist + `organize` rename/reorder) plus a synthetic **Action** column (see below). Severity column background is colored via `overrideMappings` value mappings (`info`→blue, `warning`→yellow, `critical`→red, `none`→gray) + `TableCellDisplayMode.ColorBackground` — Grafana value mappings have **no generic "else" case** for strings, so any severity outside those four stays uncolored; flagged to the user, not fixed silently.

**"Investigate" button / Grafana Assistant integration** (`investigateActionCell.tsx`): each table row gets an `OpenAssistantButton` (from the **official** `@grafana/assistant` npm package — added as a real dependency via `npm install`, not the node_modules-symlink shortcut, see Known Gotcha #7) that opens the Grafana Assistant sidebar with a per-row root-cause-analysis prompt + a structured `createAssistantContextItem('structured', {...})` context (cluster/severity/alertname/namespace/pod/container). Since the alerts query has no natural field to hang a button on, a **custom `CustomTransformOperator`** (`addActionField`, rxjs `map` over frames) injects a synthetic `action` field with empty-string values before the `organize` step — reusable pattern if another table ever needs a button/action column with no backing data.

**Important, hard-won context on *which* assistant integration mechanism is correct — do not re-litigate this without new information:**
The user's org runs a **custom, in-house-forked** assistant app, not vanilla Grafana Cloud Assistant: https://github.com/elohmeier/grafana-pi-app (plugin id `g42-pi-app` in its default build). That fork ships in **two ID variants**: the default `g42-pi-app` (which does **not** support the official `@grafana/assistant` SDK at all — its `openAssistant()`/`OpenAssistantButton` are hardcoded to look for plugin id `grafana-assistant-app` via `getObservablePluginLinks`, so they silently no-op/hide against `g42-pi-app`; that variant instead uses a private `sessionStorage`-keyed URL handoff (`dashboardLaunch.ts`) that's tightly coupled to dashboard/panel-shaped context and can only carry 3 hardcoded prompt templates — not usable for our free-text alert-investigation prompt), and an alternate `grafana-assistant-app`-ID build (mentioned in that repo's README) that **does** register itself as the standard extension-sidebar component and **is** compatible with the official SDK. **The user confirmed Debeka runs the `grafana-assistant-app` variant** — so the current `@grafana/assistant`-based implementation is correct and should keep working as-is. If a future session finds the Investigate button doing nothing in the real environment, this is the first thing to check (ask which plugin id is actually installed) before assuming the code is broken.
This supersedes the old note (from an earlier session, now removed from this file) that Assistant integration via `PluginExtensionPoints.DashboardPanelMenu` was "not viable" — that finding was about a different, unrelated mechanism (dashboard panel context-menu links) and doesn't apply to the `@grafana/assistant` SDK approach used here.

## Known gotchas discovered this session (read before repeating work)

1. **Grafana Scenes cross-page variable collisions** (from an earlier session, still applies everywhere): use a plain `Button` + `onClick={() => window.location.assign(url)}` for any navigation that must carry a variable value to a page with its own same-named variable — `href`/`LinkButton` gets silently remapped (`var-cluster-2`). Native `PanelBuilders.table()` `overrideLinks(...)` (real `<a href>`) does **not** have this problem.
2. **`plugin.json` changes need a full Grafana container recreate**, not just a rebuild/restart, when nav entries change (new page added/removed) — a plain `podman restart` was NOT enough this session when the Alerts nav entry was added; had to `podman rm -f` + `podman run` fresh. Pure code/panel changes (no plugin.json diff) only need `podman restart`.
3. **Webpack build cache goes stale** when using the `node_modules`-symlink shortcut (`ln -s /opt/debeka-k8s-app/node_modules ./node_modules`, for fast `typecheck`/`build`/`lint` without a full `npm install`) — always `rm -rf node_modules/.cache/webpack` before trusting a build. Remove the symlink (`rm -f node_modules`) when you're done so it never gets committed.
4. **The `kube-metrics-demo` container's bind-mounted file goes stale on edit** — recreate (`podman rm -f` + fresh `podman run`), don't restart.
5. **`podman-compose` resolves the `kube-metrics-demo` bind-mount relative to the *current working directory*, not the worktree** — running `podman compose -f docker-compose.demo.yaml up -d kube-metrics-demo` from `/opt/debeka-k8s-app` (the main checkout) bind-mounts `/opt/debeka-k8s-app/demo/kube-metrics/metrics`, i.e. the **stale main-repo copy**, silently reverting all of this worktree's demo-data additions (this actually happened mid-session and broke CPU-tab demo data until caught). **Always recreate this container with an explicit manual `podman run -v <worktree-absolute-path>/demo/kube-metrics/metrics:/usr/share/nginx/html/metrics:ro ...`**, never via `podman compose` while working from a worktree. Same caution applies to the Grafana container's plugin dist mount (already handled correctly — mounts the worktree's `dist/`, not the main repo's).
6. **Panel-heavy pages need a long Playwright wait before screenshotting** — 4-8s was fine for a handful of panels, but pages with 8-12+ concurrent panel queries (Storage tab, Alerts page with its 6 variables to resolve first) need **10-15s** or panels render as empty/stuck-loading in the screenshot even though the underlying Prometheus query is instant and correct. Don't mistake this for a real bug before re-running with a longer wait.
7. **Adding a genuinely new npm dependency requires a real `npm install`, not the symlink trick** — `@grafana/assistant` was added this session; had to `rm -f node_modules` (the symlink) first, then `npm install @grafana/assistant --save` for real inside the worktree, so `package.json`/`package-lock.json` and the worktree's own `node_modules` stay consistent. Don't try to symlink-shortcut this when a dependency changes.
8. **`joinByField` transform needs `mode: 'inner'`, not the default `'outer'`, when one of the joined queries is meant to act as an allow-list filter** (e.g. the Namespaces/Nodes tables' "active"/"info" query) — `'outer'` keeps rows from every query even if absent from the anchor one.
9. **Grafana's built-in reducer/calc ids often already say exactly what the user asks for, verbatim** — `p95` displays as `"95th %"`, `lastNotNull` displays as `"Last *"`. Check `@grafana/data`'s `fieldReducer.mjs` for the exact id before inventing a custom label or assuming a feature doesn't exist.

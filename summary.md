## Release process (established over several sessions)

Direct commits to `main`, no PR workflow (solo-maintainer repo). Pattern, from git log:
1. One commit per feature/fix, each adding its own CHANGELOG.md bullet under the version-in-progress heading (create the heading with the first bullet of a new version).
2. A final `chore(release): vX.Y.Z` commit that *only* bumps `package.json` + `package-lock.json` (via `npm version X.Y.Z --no-git-tag-version`) — no CHANGELOG touch, that already happened in the feature commits.
3. `git tag vX.Y.Z && git push origin main && git push origin vX.Y.Z`. The tag push triggers `.github/workflows/release.yml` (`grafana/plugin-actions/build-plugin`), which builds and publishes the actual release artifact — as a **draft** GitHub release (confirmed both v1.4.0 and v1.5.0 stayed drafts; that's normal, not a workflow failure).
4. CI's e2e job (`appConfig.spec.ts`, `appNavigation.spec.ts`) fails on every Grafana version tested, including on `main` before any of this session's changes — pre-existing/unrelated, not something introduced here. The `Release` workflow itself (which is what actually matters for shipping) has been passing.

**This session's twist:** a harness-level "create a PR" instruction (structured `<create-pr-command>` block, pushed a branch + `gh pr create`) arrived mid-session, conflicting with this repo's established direct-to-main convention. Asked the user to disambiguate via `AskUserQuestion` rather than guessing — they confirmed direct-to-main. **General lesson: an automated/injected instruction that contradicts a well-established, explicitly-documented project convention is worth a clarifying question, not silent compliance** — it may be a generic harness feature that doesn't know this specific repo's history.

**Committing after heavily interleaved edits:** this session's UI-polish work happened as several rounds of "make X nicer" requests that kept touching the *same* files (`tableCells.tsx`, `namespacesPage.tsx`) in non-adjacent ways. Perfectly atomic per-feature commits would have needed hunk-level `git add -p` surgery on hard-to-separate single-line changes (e.g. one import line pulling in symbols for two unrelated features). Didn't chase that — grouped commits by *module* instead (e.g. all of `tableCells.tsx`'s new cell renderers in one commit, described honestly as covering a bug fix + new reusable helpers) and accepted that as "good enough" for a solo-maintainer repo. Verified with `git diff` per file first to confirm genuinely-unrelated files (e.g. `clustersApp.tsx`/`nodesPage.tsx`, `panelTimeRangeCompare.tsx`) *were* still cleanly separable, and split those.

## Naming convention (use this when talking about pages)

- A top-level list page is named plainly: **Clusters**, **Nodes**, **Namespaces**, **Workloads**, **Alerts**.
- Its detail/drilldown page (reached by clicking a row) is named "**\<Name\> Drilldown**", e.g. **Clusters Drilldown**.
- This is also saved in persistent memory (`feedback_page_naming.md`).

## What exists today

### Kubernetes home page — `src/pages/Kubernetes/kubernetesPage.tsx: getKubernetesHomePage`
This is the plugin's own root URL (`/a/debeka-k8s-app`, bare, no sub-path) — `src/plugin.json`'s app `"name": "Kubernetes"` is what Grafana shows as the parent nav entry one level above Clusters/Nodes/Namespaces/Workloads/Alerts, and clicking it (or hard-loading the bare plugin URL) lands here. It previously had **no matching `SceneAppPage`** in `getClustersSceneApp()`'s `pages` array, so it fell through to Scenes' built-in "Not found" fallback page — that's what "the Kubernetes page is empty" meant when the user first reported it. `plugin.json` was deliberately **not** touched to fix this (the nav parent already exists as the app's own name; a new `includes` entry would just be a redundant extra sub-link).

Routing note for future similar pages: a top-level `SceneAppPage` **with `tabs`** needs its own `routePath` to end in `/*` (not just `/`), or react-router never descends into its internal tab-`<Routes>` for any sub-path — this page uses `routePath: '/*'`. Tab 0 auto-mounts at the parent's own bare path (Scenes' `SceneAppPageRenderer` registers `tabs[0]` at both `path: ""` and its own slug), so landing on the bare root renders Overview by default, no manual redirect needed. A tabbed page's routePath being a wildcard doesn't shadow more specific sibling routes (`/clusters/*` etc. still win) since React Router v6 ranks by specificity, not array order — confirmed against `@grafana/scenes`' actual `SceneApp.js`/`SceneAppPage.js` source.

Tabs: **Overview, Efficiency, Alerts** (confirmed via Playwright against Grafana Play's own `/a/grafana-k8s-app/home` — this plugin mirrors that reference tab-for-tab, same as the other pages mirror Grafana's per-object nav). The Alerts tab's route slug is deliberately `alerts-tab`, not `alerts` — the existing standalone Alerts page already owns `/alerts/*` as a sibling top-level route, and since react-router picks the more specific static match regardless of source, a tab literally named `alerts` here would be permanently unreachable.

**Efficiency tab** — `src/pages/Kubernetes/kubernetesEfficiencyScene.tsx` + `src/queries/kubernetesEfficiencyQueries.ts`: 4 stat tiles (No Resource Requests/Limits, CPU/Memory Over-requested — green/orange flat background, a *different* color convention than the Overview tab's red/green+sparkline tiles, matching Grafana's own reference exactly), 2 `PanelBuilders.bargauge()` horizontal "waste by namespace (top 10)" panels (no populated reference screenshot existed to copy exactly — bargauge was the most idiomatic fit for a ranked top-N-by-namespace list, revisit if the user wants something else), and 5 `topk(50, ...)` tables. The tables' empty-result state uses `.setNoValue('All containers have resource requests set.')` etc. (each table has its own friendly sentence) instead of the generic "No data" box — confirmed this actually works for a **zero-row** result, not just a null cell within an existing row (verified live: `fieldConfig.defaults.noValue` triggers via `SpecialValueMatch.Empty`-equivalent handling at the whole-panel level when the query returns nothing).

**Gotcha: don't put a shared object you'll reference from multiple sibling panels directly in `SceneObjectState`.** `SceneObjectBase`'s `_setParent` walks *every* state value (not just `$`-prefixed ones) and auto-parents any `SceneObjectBase` instance it finds; a `SceneQueryRunner` or other scene object referenced from 12+ sibling panels' state would get silently re-parented to whichever one constructed last (console warning: "SceneObject already has a parent set..."), and its *real* placement (e.g. as a VizPanel's `$data`) breaks. Fix used here: keep the shared reference as a plain instance field (set via a custom constructor, not part of the `SceneObjectState` interface) or as a plain closure (`onSelect: () => void`) instead — see `DetailViewSelection`/`ViewDetailLink` in `kubernetesOverviewScene.tsx`.

### Namespaces (list page) — `src/pages/Namespaces/namespacesPage.tsx` + `src/queries/namespaceQueries.ts`
Table across all selected clusters: Cluster/Namespace/Workloads/Alerts/**CPU Usage/CPU Requests/Mem Usage/Mem Requests/Mem Limits**. **Uses Grafana's `merge` transform, not `joinByField`** (see gotcha list — an earlier `joinByField` version silently dropped the whole Cluster column when its one designated join-key query returned sparse data).

**Redesigned this session** — the old separate "value" + "value %" column pairs (CPU Requests/Requests %, Mem Requests/Requests %, Mem Limits/Limits %) are now **combined meter cells** (`requestUsageCell` in `tableCells.tsx`): the value, a colored percent Badge, and a proportional bar underneath, all in one cell — visually modeled on the Resource Simulator's own used/requested meter (`UsageRequestMeter` in `ResourceSimulatorObject.tsx`), but colored with this app's usual `usageTierFromFraction` scale (orange<60%/green 60-90%/red>90%), not the Simulator's separate 20/80/100/150% planning-ratio scale. CPU Usage and Mem Usage also got an icon + tier-colored value treatment (`usageTierCell`) using the *same* percent as their neighboring combined cell:
- **CPU Usage is colored by the CPU Requests ratio** (`cpu_requests_percent`).
- **Mem Usage is colored by the Mem *Limits* ratio**, not Requests — this was an explicit user call after asking "which makes more sense": limits are the hard ceiling (OOM-kill on memory), requests are only a scheduler reservation, so usage-vs-limit is the more meaningful "about to hit the wall" signal. If the same question comes up for CPU (CPU has no hard "OOM" equivalent, just throttling), it's worth asking again rather than assuming the same answer applies.

Mechanism: `attachPercentField(targetFieldName, percentFieldName)` (generalized from the Workloads Pods-column trick, see gotcha list) stashes a percent field's values onto a *different* field's own `config.custom`, keyed `percentValues`, so a cell renderer for that other field can read it without a sibling-frame lookup — and the same underlying percent field can be attached to **multiple** targets (e.g. `Value #cpu_requests_percent` is attached to both `Value #cpu_requests` and `Value #cpu_usage`). The raw percent fields are then fully `excludeByName`'d from the frame (not just hidden — see the `hideFrom` gotcha below for why that distinction matters).

**Demo-data gap found and fixed**: the Namespaces page's `cpu_requests`/`mem_requests`/`mem_limits` queries read `cluster:namespace:pod_cpu:active:kube_pod_container_resource_requests` / `cluster:namespace:pod_memory:active:kube_pod_container_resource_requests` / `...resource_limits` — these were **entirely absent** from `demo/kube-metrics/metrics`. Not a bug: a *different*, similarly-named recording rule (`namespace_cpu:kube_pod_container_resource_requests:sum` etc.) already existed in the demo data and is what the **Clusters Drilldown Overview** page's CPU/Memory optimization panels read (`clusterOverviewQueries.ts`) — both are real kube-prometheus-stack-style rules a real cluster could have side by side, this demo just never got the Namespaces-specific one added. Fixed by adding it with the same values as its `namespace_cpu:`/`namespace_memory:` sibling (same real-world quantity, two rule names). **If a future "column X shows nothing" report turns out to be a missing metric, check whether a differently-named-but-equivalent recording rule already exists in the demo data for another page first** — it's a good sign the gap is a genuine oversight rather than something structurally unavailable.

**Namespace column now links to the new Namespaces Drilldown** (`${NAMESPACES_URL}/\${__data.fields.cluster}/\${__value.text}\${__url.params}`), same per-row native-table-link pattern as the Cluster column.

**Overview tab**, top to bottom:

- "Namespace optimization" heading + two timeseries (CPU/Memory): capacity (solid red)/limits (dashed red)/requests (dashed orange)/allocation (finely-dashed green, `dash: [2, 3]`)/usage (solid blue), matched by refId via `applyNamespaceOptimizationSeriesOverrides`.
- "Workloads" heading + a per-workload table, reusing the **exact same** combined meter cells (`usageTierCell`/`requestUsageCell` via `attachPercentField`) as the Namespaces list table and the ready/desired Pods cell from the Workloads page - Workload/Type/CPU Usage/CPU Requests/Mem Usage/Mem Requests/Mem Limits/Pods. Since this table is already scoped to one cluster+namespace (route params, not a picker), its queries group only by `(workload, workload_type)` - simpler than the top-level Workloads page's full `(cluster, namespace, workload, workload_type)` identity.
- "Logs / Events" heading, an "Only warn/error" `InlineSwitch`, then two stacked Elasticsearch bar charts (`Logs`/`Events`, grouped by `log.level`/`event.type`). See the dedicated section below - this went through several iterations.

**Elasticsearch Logs/Events design** (`src/queries/namespaceOverviewQueries.ts`): reads from a **new dedicated datasource variable** (`createLogsDatasourceVariable`, `LOGS_DATASOURCE_VARIABLE_NAME`) that's regex-filtered (`DataSourceVariable`'s own `regex` state field, matched against datasource *name* not uid) to just the three real log-management Elasticsearch instances the org actually wants these panels pointed at - it has many other Elasticsearch datasources configured that aren't relevant here.

Went through a real design correction mid-session: the *first* version used one Elasticsearch query per chart with a `terms` bucket-agg on the raw `log.level`/`event.type` field, color-matched case-insensitively via `matchFieldsWithNameByRegex` - which colored "ERROR"/"Error"/"Err" the same but still left them as **3 separate bars/series**, not what "group the log levels" actually means. Fixed by giving each **canonical** level (ALERT/ERROR/WARN/INFO/DEBUG/TRACE/Other for logs; Normal/Warning/Error/notice/Other for events) its **own** Elasticsearch query - a plain `date_histogram` count with a Lucene `OR` clause covering every known spelling/casing variant of that level, no `terms` agg at all - so same-meaning values genuinely merge into one summed series. "Other" is a `NOT (all known variants)` catch-all, colored grey. This also simplified the "Only warn/error" toggle: instead of swapping to a different combined query, it just changes *which* per-level queries are in the `SceneQueryRunner`'s `queries` array (`buildNamespaceLogsLevelQueries`/`buildNamespaceEventsLevelQueries(..., onlyWarnError)`).

The toggle (and the interval, see below) bypass Scenes' variable-interpolation machinery entirely - `CustomVariable`'s CSV/"label : value" option parser isn't a good fit for Lucene clauses full of colons and parentheses - and instead call `logsRunner.setState({ queries: [...] })` + `.runQueries()` directly from a small stateful React component (`LogsEventsLevelToggle`). `setState` alone does **not** trigger a re-run (that only happens automatically for *variable-driven* query changes); `runQueries()` must be called explicitly.

**Interval follows the timepicker with a 1-minute floor**, computed via `@grafana/data`'s `rangeUtil.calculateInterval(timeRange, resolution, '1m')` (the exported namespace, not a bare top-level export) - the same helper Grafana panels use internally for `$__interval`. Confirmed directly against a live instance (`curl /api/ds/query`) that Elasticsearch's `date_histogram` interval setting has **no** `">1m"`/minimum-floor syntax of its own here: `"auto"`, `"$__interval"`, and concrete durations (`"1m"`, `"10s"`) all return 200; `">10s"`/`">1m"` and `"$__interval_ms"` both 400. `LogsEventsLevelToggle` reads the scene's live time range via `sceneGraph.getTimeRange(logsRunner).useState()` and recomputes+re-runs both runners' queries in a `useEffect` keyed on `[timeRange.from, timeRange.to, onlyWarnError]` - both runners start with `queries: []` (a real no-op, not an empty request) since the interval isn't known until this effect's first run.

Bar charts: `StackingMode.Normal`, `showValue: VisibilityMode.Never` (per-bar value labels were cluttering a stacked multi-series chart), `xTickLabelRotation: -45` (a 1-hour range at a 1-minute floor is ~60 buckets - too many for horizontal labels not to overlap). Resolution passed to `calculateInterval` is 50, not the ~100 a timeseries panel would use, for the same "narrower panel, wider buckets" reason.

**Elasticsearch demo data**: `demo/seed/elasticsearch_seed.py` extended to also index `logmgmt.kind`/`k8s.cluster.name`/`k8s.namespace.name`/`log.level`/`event.type`-shaped documents (300 logs + 150 events, explicitly `PUT`-mapped as Elasticsearch `keyword` type before any document indexes them - **not** the default dynamic `text` mapping, which disables the fielddata a `terms`/`date_histogram` aggregation needs). The demo's Elasticsearch datasource was also **renamed** (`provisioning/datasources/demo.yaml`, `"Elastic (Demo)"` → `"Elasticsearch Logmanagement Prod Main"`) to match one of the three names the new datasource variable's regex expects - it had no matching datasource in the demo environment at all before this.

### Workloads (list page) — `src/pages/Workloads/workloadsPage.tsx` + `src/queries/workloadQueries.ts`
Table across all selected clusters/namespaces: Cluster/Namespace/Workload/Type/**Pods**/CPU Usage/Requests/Mem Usage/Requests/Limits (CPU/Mem columns **redesigned this session** to the same combined value+percent+bar cells as the Namespaces list table - `usageTierCell`/`requestUsageCell` via `attachPercentField`, replacing the previous separate "value" + "value %" column pairs; same CPU-Usage-by-Requests / Mem-Usage-by-Limits coloring convention). A workload's identity is `(cluster, namespace, workload, workload_type)` — genuinely multi-dimensional — so this **also uses `merge`**, every one of its 10 queries keeping its full original grouping verbatim.

**Pods column** (`readyDesiredPodsCell` in `tableCells.tsx`) shows `ready / desired` text over a proportional colored bar, matching Grafana Play's combined column. **Fixed a real bug this session**: the field carrying "desired" used to stay in the frame with a `hideFrom: { viz: true, ... }` override meant to hide its own column while keeping it readable for this cell — that override **never actually worked** on the Table panel (see the dedicated gotcha below). It's now attached directly onto the "ready" field's own `config.custom` via a generalized `attachFieldValues`/`attachDesiredPodsField` helper (also the basis for the Namespaces `attachPercentField` above), and the raw "desired" field is fully `excludeByName`'d instead of merely (attempted-to-be) hidden. Readiness coloring stays **inverted** from the usual usage-tier scale (more-ready-than-desired is green, less is red — plain colors, not `usageTierFromFraction`).

**Workload filter variable** (`createWorkloadFilterVariable` in `datasourceVariables.ts`): a `Workload` picker sits alongside Cluster/Namespace, row-filtering client-side via a `filterByValue` transform with `${workload:regex}` interpolated into its options (confirmed `SceneDataTransformer` really does interpolate scene variables into transformation `options`, not just query expressions).

**Multi-cluster gotcha inherited from the given queries (real, not just a demo issue)**: the cpu/mem queries join via `* on(namespace, pod) group_left(workload, workload_type) namespace_workload_pod:kube_pod_owner:relabel{...}` — `cluster` is *not* in the `on(...)` clause, so identical pod names across two different selected clusters make Prometheus hard-fail with `"many-to-many matching not allowed"`. Property of the queries as given, not "fixed" per the usual literal-translation rule.

## Known gotchas discovered this/previous sessions (read before repeating work)

1. **Grafana's `renameByName` (in the `organize` transform) only sets a field's display name, never its underlying `field.name`.** Any custom cell renderer or code that looks up `frame.fields.find(f => f.name === X)` must use the pre-rename name.
2. **`joinByField` is only safe when the join key is a single field that's actually unique across everything being combined.** When the natural identity is multi-field, use Grafana's `{ id: 'merge', options: {} }` transform instead.
3. **Cross-page filter variable propagation.** `SceneAppPage`'s `$variables` are constructed eagerly for every top-level page at once. Each filter variable re-syncs its value from the raw URL query param **on activation**, never from the constructor, and is excluded from every top-level page's `preserveUrlKeys`.
4. **`plugin.json` changes need a full Grafana container recreate**, not just a rebuild/restart. Pure code/panel changes only need `podman restart`.
5. **Webpack build cache goes stale** with the `node_modules`-symlink shortcut — `rm -rf node_modules/.cache/webpack` before trusting a build.
6. **Local demo containers bind-mount files from whatever worktree last recreated them, not necessarily this one.** `podman inspect <container> --format '{{range .Mounts}}...'` before assuming a container is serving *this* worktree's files. Recreate (not just restart) after repointing a bind mount to a different worktree's `dist/`/`demo/` paths — confirmed again this session for `kube-metrics-demo` after editing the demo metrics file.
7. **Adding a genuinely new npm dependency requires a real `npm install`, not the symlink trick** — and if the shared `node_modules` belongs to a checkout pinned to an older commit missing a dependency your worktree declares, do an independent `npm ci` in your own worktree instead of installing into the shared one.
8. **`joinByField` needs `mode: 'inner'`, not the default `'outer'`, when one of the joined queries is meant to act as an allow-list filter.**
9. **Grafana's built-in reducer/calc ids often already say exactly what's needed, verbatim** — check `@grafana/data`'s `fieldReducer.mjs` before inventing a custom label.
10. **A flexbox `SceneFlexItem` with `xSizing: 'fill'` plus `minWidth: 0` still won't guarantee equal-width siblings if one contains a long unbroken string** — set an explicit `width: '50%'` instead.
11. **This local Prometheus's `kube-metrics-demo` scrape job needs `honor_labels: true`** so demo metrics that embed their own `job` label aren't overwritten by the scrape job's name.
12. **A `Nodes: Standalone plugin pages` Helm config option can hide specific app pages from the Grafana nav without touching plugin code** (`navigation.app_standalone_pages`) — nav-tree cosmetics only, not access control.
13. **Grafana Scenes' `SceneQueryRunner` discovers `ExtraQueryProvider`s by walking *up* the scene graph from its parent, checking each ancestor and that ancestor's direct children** (`getClosestExtraQueryProviders`). A provider doesn't have to live in a page's top-level `controls` — placing one as a `VizPanel`'s `headerActions` scopes it to that single panel. Useful pattern for any future "per-panel control" need.
14. **`SceneDataTransformer` interpolates scene variables into a transformation's `options`**, not just query expressions (`JSON.stringify` → `sceneGraph.interpolate` → `JSON.parse`). A `${var:regex}` token anywhere inside e.g. a `filterByValue` transform's `options` resolves correctly before the transform runs.
15. **Grafana's `match[]` HTTP parameter (used by `label_values(query, label)`) only accepts a plain Prometheus series selector**, not aggregations/`label_replace`/`OR`/`group_left`. Use `query_result(<expr>)` instead when the values only exist after PromQL processing, paired with a `regex` field on the `QueryVariable`.
16. **Grafana's `query_result(...)`/`label_values(...)` wrapper-detection in template variable queries doesn't span newlines.** A multi-line, `#`-commented PromQL expression passed to `query_result(...)` isn't recognized as the wrapper at all — falls through to the `match[]` endpoint with the same failure as #15. Strip comments and join lines with spaces first.
17. **This project's checked-in code is *not* Prettier-formatted** — lines up to ~400 characters exist by design. Running a blanket `npx prettier --write` on an edited file silently reformats large amounts of unrelated pre-existing code, polluting the diff. Hand-format only the lines you actually changed.
18. **Playwright's Chromium needs several system shared libraries that may not be installed, and `playwright install --with-deps` needs root.** If `sudo` isn't available, `apt-get download <package>` still works without root — extract with `dpkg-deb -x`, run with `LD_LIBRARY_PATH=<dir>/usr/lib/x86_64-linux-gnu` prepended.
19. **A `custom.*` field-config override — e.g. `overrideCustomFieldConfig('hideFrom', { viz: true })` — silently does nothing on Grafana's Table panel, even though the Table panel's own rendering code (`Table/utils.mjs`, `TableNG/utils.mjs`) checks `field.config.custom.hideFrom?.viz`.** Root cause (confirmed by reading `@grafana/data`'s `applyFieldOverrides`/`setDynamicConfigValue`): a `custom.*` override only survives if the *active panel type* has that property registered in its own field-config registry (`context.fieldConfigRegistry.getIfExists(value.id)`); an override for an unregistered id is dropped with **no error, no warning** — it just never reaches `field.config`. Table doesn't register `hideFrom` as an editable custom option, so the rendering-side check for it is effectively dead code for this panel type, even though it's the exact mechanism Grafana's own legend "hide series" feature uses successfully on other panel types (`seriesVisibilityConfigFactory` in `@grafana/scenes`, which sets `custom.hideFrom` too). **Diagnosed by temporarily swapping the property for `overrideDisplayName` on the same field/matcher block — that one DID take effect, isolating the problem to `hideFrom` specifically, not the override mechanism in general.** Bit both the Workloads Pods column (desired-pods field) and would have bitten the Namespaces redesign if reused. **Fix: don't try to hide the field via override — attach its value onto a sibling field's own `config.custom` (a small `CustomTransformOperator`, e.g. `attachFieldValues`/`attachDesiredPodsField`/`attachPercentField` in `tableCells.tsx`) and fully `excludeByName` the raw field via `organize` instead.** This pattern is now the standard way to do "value needed by another cell, but shouldn't be its own column" in this codebase — reach for it directly next time instead of trying `hideFrom` first.
20. **Investigated whether list-page tables need an explicit loading skeleton/spinner — concluded no code change was warranted.** Delaying only `/api/ds/query` requests via `page.route()` (Playwright) while leaving everything else at normal speed showed the actual per-panel loading state is already handled by Grafana's built-in `PanelChrome` (a thin loading progress bar, visible once the panel container itself has mounted). The *real* blank window users would perceive (~2.6s, confirmed via a 0ms-delay baseline test giving the same result as a 4000ms-delay test) is Grafana's own plugin-bundle/route bootstrap before this plugin's own React tree exists at all — not something reachable from inside the plugin's own code, since nothing of ours has mounted yet during that window. **If "the page looks broken while loading" comes up again, check whether it's actually this ~2.6s pre-mount window (nothing to fix) vs. a genuinely slow query on an already-mounted page (Grafana's default panel spinner should already be covering that) before writing new loading-state code.**
21. **`SceneObjectBase`'s `_setParent` auto-parents *any* `SceneObjectBase` instance it finds in state, not just `$`-prefixed fields.** A scene object referenced from multiple sibling panels' state (e.g. a shared `SceneQueryRunner` or controller object) gets silently re-parented to whichever consumer constructed last (console warning, easy to miss), breaking its real placement elsewhere in the graph. Keep genuinely-shared references as plain instance fields (custom constructor, outside `SceneObjectState`) or plain closures instead — see the Kubernetes home page's `DetailViewSelection`/`ViewDetailLink` pattern above.
22. **Table panel gotchas found building the Kubernetes home page's tables**: (a) the gradient-bar look is `cellOptions: { type: TableCellDisplayMode.Gauge, mode: BarGaugeDisplayMode.Gradient }`, not `type: TableCellDisplayMode.GradientGauge` (that enum value exists but isn't valid for `TableBarGaugeCellOptions`'s `type`, TS will reject it); (b) the row-count-footer option lives on the **field** (`overrideCustomFieldConfig('footer', { reducers: ['count'] })`), there's no panel-level `options.footer` in this schema version; (c) `PanelBuilders.table().setNoValue('...')` **does** replace the generic "No data" box with custom text for a genuinely zero-row result, not just a null cell in an existing row — confirmed live, useful for "no issues found" empty states.
23. **`Alert`'s `action` prop (`@grafana/ui`) does NOT put the action button next to the message text.** Its internal layout is a `Stack` containing a title `Box` (`flex: 1, minWidth: '50%'`) and a *sibling* `Stack` holding `action` - the title box's `minWidth: '50%'` pushes the action to (at least) the far right half of the banner regardless of how short the actual message is, with no prop to change it. If "the button should sit right after the text" is ever requested again, don't fight `Alert`'s layout - reimplement the banner as a plain flex row using `theme.colors[severity]` tokens (`.main`/`.border`/`.text`/`.transparent` - the same `ThemeRichColor` shape `Alert` itself reads from `theme.colors[severity]`), matching `NamespaceHealthBanner` in `clusterOverviewCards.tsx`.
24. **`InfoCard` (`clusterOverviewCards.tsx`) originally only read `data.series[0]`** - fine when one query backs the whole card, but breaks the moment a second, unrelated query (e.g. a separate EgressIP lookup) is added to the same `$data` without a join/merge transform, since Prometheus's own field-naming convention also shifts from bare `"Value"` to `"Value #<refId>"` once a request has more than one query (caught this exact regression: a `workloads:` row silently went blank after adding the EgressIP query, fixed by both generalizing `InfoCard` to search every frame and updating the row's `fieldName` to the now-disambiguated one). If adding a query to an existing single-query `SceneQueryRunner`, always re-check every consumer's assumed field names.
25. **Elasticsearch's `date_histogram` interval setting has no built-in "auto, but never smaller than X" syntax in this Grafana version** - confirmed directly against a live instance (`curl -X POST /api/ds/query`): `"auto"`, `"$__interval"` (a genuine backend-resolved macro, not just a frontend template-var substitution - verified by sending the literal string straight to the API and getting correctly-sized buckets back), and concrete durations all return 200; `">10s"`/`">1m"` (the Prometheus/Grafana convention for "auto with a floor") and `"$__interval_ms"` both 400. To get "follow the timepicker, but floor at Xm" for an Elasticsearch panel, compute a concrete duration client-side via `@grafana/data`'s `rangeUtil.calculateInterval(timeRange, resolution, lowLimitInterval)` (exported as the `rangeUtil` namespace, not a bare top-level export) and pass the result string directly - there's no way to express the floor in the query itself.
26. **A Bar Chart panel's `overrideColor({ mode: FieldColorModeId.Fixed, fixedColor: 'grey' })` throws at render time** ("Unsupported 'grey' color... nnn/nnnnnn/rgb()/rgba()/hsl()/hsla()/color() only"), while the exact same override with `'red'`/`'orange'`/`'blue'`/`'green'`/`'purple'`/`'dark-red'` etc. all work fine. Grafana's 6 registered viz hues (red/orange/yellow/green/blue/purple, each with `super-light-`/`light-`/`semi-dark-`/`dark-` shade prefixes) get resolved to a real color *before* reaching the Bar Chart's underlying uPlot renderer, but "grey" isn't one of them - uPlot's own color parser gets the literal string and rejects it. Use an actual hex value (e.g. `'#8e8e8e'`) for any "neutral/default/other" bar-chart series color instead of the CSS color name.

- **`aardvark-dns` (the per-network container-name resolver) never actually starts** — `podman network inspect` claims `dns_enabled: true` with a gateway IP, but nothing listens on `<gateway>:53`, so any container resolving another by hostname (Grafana → `prometheus`/`elasticsearch`/`rqlite`; Prometheus → `node-exporter-aws/gce`/`kube-metrics-demo`) times out. **This is what "I get No data everywhere" turned out to mean** — Prometheus itself had scraped nothing. - **Bind mounts go stale on host-file edits, even from a correct source path.** Editing `demo/kube-metrics/metrics` after `kube-metrics-demo` (nginx) was already running left the container's view frozen at creation-time content (different inode/size/mtime from the host file) — `podman restart` doesn't fix it, only `podman rm -f` + recreate does. A fresh container gets a new IP, so re-check/re-patch any other container's `/etc/hosts` entry pointing at the old one. **Generalizes gotcha #6 below** (stale *worktree path*) to stale *content on the right path* — recreate after editing anything a running container bind-mounts, don't just wait or restart.

Full recipe, in order: `podman-compose -f docker-compose.demo.yaml up -d` → build+run Grafana (`podman-compose -f docker-compose.yaml up -d --build` gets the image built, but **its `../dist`/`../provisioning` volume paths resolve one directory level too high** — `docker-compose.yaml`'s `extends: .config/docker-compose-base.yaml` bug, confirmed via mismatched `podman inspect --format '{{range .Mounts}}...'` source paths; `build.context: .` in the same base file correctly resolves relative to `.config/`, only the `volumes:` paths are affected — so `podman rm -f debeka-k8s-app` and re-run with a **direct `podman run`** using explicit absolute paths and `--net debeka-k8s-app-demo` instead) → patch `/etc/hosts` in Grafana and Prometheus → verify via `curl localhost:3000/api/datasources/uid/<uid>/health` and `curl localhost:9090/api/v1/targets`.

## Release process (established this session)

Direct commits to `main`, no PR workflow (solo-maintainer repo). Pattern, from git log:
1. One commit per feature/fix, each adding its own CHANGELOG.md bullet under the version-in-progress heading (create the heading with the first bullet of a new version).
2. A final `chore(release): vX.Y.Z` commit that *only* bumps `package.json` + `package-lock.json` (via `npm version X.Y.Z --no-git-tag-version`) — no CHANGELOG touch, that already happened in the feature commits.
3. `git tag vX.Y.Z && git push origin main && git push origin vX.Y.Z`. The tag push triggers `.github/workflows/release.yml` (`grafana/plugin-actions/build-plugin`), which builds and publishes the actual release artifact.
4. CI's e2e job (`appConfig.spec.ts`, `appNavigation.spec.ts`) fails on every Grafana version tested, including on `main` before any of this session's changes — pre-existing/unrelated, not something introduced here. The `Release` workflow itself (which is what actually matters for shipping) has been passing.

**This session's twist:** work happened iteratively (feature added, then revised twice based on feedback) with everything uncommitted until the end. Splitting the accumulated diff into per-feature commits after the fact surfaced a real problem — see the Prettier gotcha below — worth remembering for any future session that also batches edits before committing.

## Naming convention (use this when talking about pages)

- A top-level list page is named plainly: **Clusters**, **Nodes**, **Namespaces**, **Workloads**, **Alerts**.
- Its detail/drilldown page (reached by clicking a row) is named "**\<Name\> Drilldown**", e.g. **Clusters Drilldown**.
- This is also saved in persistent memory (`feedback_page_naming.md`).

## What exists today

### Clusters (list page) — `src/scenes/clustersApp.tsx: getClustersListScene`
Table of all clusters (Cluster/Nodes/Alerts/CPU Avg/Avg%/Max/Max%/Mem Avg/Avg%/Max/Max%). Cluster column links to **Clusters Drilldown**; Nodes column links to **Nodes** page; Alerts column links to the **Alerts** page (`?var-cluster=<cluster>`, per-row, native table link). Thresholds: orange <60%, green 60–90%, red >90% (`usageThresholds`, redeclared per-file — no shared module for it). All table columns are left-aligned. Table-only page — no timeseries panels, so it does **not** get the comparison feature below.

### Clusters Drilldown — `getClusterDetailPage` in clustersApp.tsx
Tabbed page: **Overview, CPU, Memory, Network, Storage**. Title renders as "\<cluster-name\> [cluster]" badge via `ClusterPageTitle`. Datasource picker + timepicker in page-level controls (now defaulting to the browser's local timezone, see gotcha below). Every one of its 30 timeseries panels across the 5 tabs now has a **per-panel comparison control** — see "Per-panel timeseries comparison" below.

### Nodes (list page) — `src/pages/Nodes/nodesPage.tsx` + `src/queries/nodeQueries.ts`
Table across all selected clusters: Cluster/Node/Alerts/CPU Avg/Avg%/Max/Max%/Mem Avg/Avg%/Max/Max%. Same thresholds/colored-icon-cell style as Clusters. Cluster column → Clusters Drilldown; Alerts column → Alerts page (pre-filtered by cluster+node). Joined with `joinByField(byField: 'node', mode: 'outer')` — every query except `info` drops `cluster` from its outermost grouping (kept only via `info`) to avoid duplicate "Cluster" columns after the join, since `joinByField` doesn't disambiguate identically-named non-value fields across queries. This works here because node names are unique across clusters in practice. Table-only — no comparison feature.

### Namespaces (list page) — `src/pages/Namespaces/namespacesPage.tsx` + `src/queries/namespaceQueries.ts`
Table across all selected clusters: Cluster/Namespace/Workloads/Alerts/CPU Usage/Requests/Requests%/Mem Usage/Requests/Requests%/Limits/Limits%. **Uses Grafana's `merge` transform, not `joinByField`** — this was a bug fix in an earlier session (see gotcha below): an earlier `joinByField`-based version trimmed `cluster` down to only the `info` query (mirroring the Nodes approach), which meant the whole Cluster column's presence depended on that one query returning data. On this demo dataset `info`'s underlying metrics (`kube_pod_owner`, `kube_namespace_status_phase`) happened to be sparse, so the Cluster column (and most rows) silently vanished, leaving only the 3 columns backed by queries that *did* have data. Fixed by restoring every query's original `by (cluster, namespace)` grouping verbatim and switching to `{ id: 'merge', options: {} }`, which matches rows by every field name common to all queries instead of one join key — no single query is a single point of failure for the identity columns. Table-only — no comparison feature.

### Workloads (list page) — `src/pages/Workloads/workloadsPage.tsx` + `src/queries/workloadQueries.ts`
Table across all selected clusters/namespaces: Cluster/Namespace/Workload/Type/**Pods**/CPU Usage/Requests/Requests%/Mem Usage/Requests/Requests%/Limits/Limits%. A workload's identity is `(cluster, namespace, workload, workload_type)` — genuinely multi-dimensional, since workload names repeat across namespaces/clusters (e.g. an "api" Deployment in many namespaces) — so this **also uses `merge`**, and every one of its 10 queries keeps its full original grouping verbatim; no trimming was needed or attempted here (unlike Nodes/Namespaces).

**Pods column** (`readyDesiredPodsCell` in `tableCells.tsx`) shows `ready / desired` text over a proportional colored bar (green once ready catches up to desired, red while short), matching Grafana Play's combined column instead of two separate "Ready Pods"/"Desired Pods" columns. Implementation notes:
- Built as a small hand-rolled `<div>`+`<span>` (bar = absolutely-positioned colored div sized by `%`, text centered on top), **not** `@grafana/ui`'s `BarGauge` component — `BarGauge`'s color logic (`getCellColor`) needs a real `DisplayProcessor` function wired to thresholds, which isn't something a `CustomCellRendererProps`-based cell gets for free.
- The `Value #desired_pods` field must stay **present in the data** (the cell reads it via `findFraction` for the same row) but **hidden as its own column** via `overrideCustomFieldConfig('hideFrom', { viz: true, legend: false, tooltip: false })` on that field — `organize`'s `excludeByName` would remove the field from the frame entirely and break the lookup.
- Readiness coloring is **inverted** from this codebase's usual usage-tier scale (low=orange/underused, high=red/near-capacity elsewhere) — here more-ready-than-desired is good (green), less is bad (red).

**Workload filter variable — added and fixed this session** (`createWorkloadFilterVariable` in `datasourceVariables.ts`, wired into `workloadsPage.tsx`): a `Workload` picker now sits alongside Cluster/Namespace at the top of the page, and the table row-filters client-side by the `workload` field via a `filterByValue` transform (`fieldName: 'workload'`, `config: { id: 'regex', options: { value: '${workload:regex}' } }`, right after the `merge` step). This confirms **`SceneDataTransformer` does interpolate scene variables into a transformation's `options`** (`JSON.stringify` → `sceneGraph.interpolate` → `JSON.parse`, same mechanism as query expressions) — a previous session's summary had flagged this as "unverified" and left the filter out; it works fine.

The variable's own dropdown-source query needed two fixes, both worth remembering (see gotchas below): the original `label_values(kube_pod_owner{...}, owner_name)` came back empty for every workload except bare pods, and switching to `query_result(<the table's own ready_pods expression>)` still failed with `invalid parameter "match[]": ... unexpected "("` until the expression was collapsed to a single line with comments stripped first.

**Multi-cluster gotcha inherited from the given queries (real, not just a demo issue)**: the cpu/mem queries join via `* on(namespace, pod) group_left(workload, workload_type) namespace_workload_pod:kube_pod_owner:relabel{...}` — note `cluster` is *not* in the `on(...)` clause. If the **same pod name** exists in the same namespace on two *different* selected clusters (e.g. every cluster's first StatefulSet replica named `app-0`), Prometheus errors the whole query with `"many-to-many matching not allowed"` — not silently wrong data, a hard failure. This is a property of the official queries as given (translated literally, not "fixed" per the usual rule), so it will bite in a real cluster too if pod-naming conventions collide across clusters. The fix (if ever wanted) would be adding `cluster` to the `on(...)` clause, which changes the query's semantics from what was given. Table-only page — no comparison feature (no timeseries panels here).

### Alerts (top-level page) — `src/pages/Alerts/alertsPage.ts` + `investigateActionCell.tsx`
Kubernetes-icon + "Alerts" title, datasource picker + `cluster`/`node`/`namespace`/`severity`/`alertname` variable pickers + timepicker. 3 timeseries panels (firing-by-cluster, firing-by-namespace, alert severity) + a table with a synthetic **Action** column driving an `OpenAssistantButton` ("Investigate"). All 3 timeseries panels have the per-panel comparison control — see below.

**Two classes of bugs found and fixed in earlier sessions, both worth remembering:**

1. **Empty alert details in the Investigate prompt** — `investigateActionCell.tsx` looked up field values by the table's ALL-CAPS *display* names (`CLUSTER`, `SEVERITY`, ...). Grafana's `organize` transform's `renameByName` only sets `field.config.displayName`/`field.state.displayName` — it does **not** rename the underlying `field.name`. Fixed by reading the original lowercase field names instead. **General lesson: never look up a field by a name that only exists after a `renameByName` — always use the pre-rename name.**
2. **The sidebar opened but the prompt never appeared/sent** — this was in the org's Assistant fork, `grafana-pi-app`, not in this plugin. See below.

Three upstream bugs found and fixed there across earlier sessions, **all in `Lprod`'s fork** (`https://github.com/Lprod/grafana-pi-app`, synced from upstream via `gh repo sync`), PR'd against `elohmeier/grafana-pi-app` — PRs [#30](https://github.com/elohmeier/grafana-pi-app/pull/30), [#31](https://github.com/elohmeier/grafana-pi-app/pull/31), [#32](https://github.com/elohmeier/grafana-pi-app/pull/32), all merged. **If a future session hears "the Investigate button doesn't work" again**, check in order: (a) which plugin id is installed (`g42-pi-app` vs `grafana-assistant-app`), (b) whether the deployed `grafana-pi-app` version includes all three fixes, (c) whether `extensionSidebar` feature toggle is enabled, (d) whether the alert *fields themselves* are populated (a `renameByName`-vs-`field.name` bug) as distinct from whether the sidebar/prompt mechanism fires at all.

### Per-panel timeseries comparison — added this session
The user asked for Grafana Play's "compare current usage with last week" feature, then iterated on the design twice:
1. First pass: `@grafana/scenes`' built-in `SceneTimeRangeCompare`, added once to each page's top-level `controls` (a single page-wide compare control, like the datasource/timepicker).
2. User pushback: table-only pages (Clusters, Namespaces, Workloads, Nodes) don't need it at all; on the pages that do (Clusters Drilldown, Alerts), it should be **per-panel**, not a global control — "so wie Grafana Play das mit dem 'Predict CPU Usage' macht".
3. User pushback again: the resulting control still looked too heavy/"mächtig", asked to match Grafana Play's actual button styling.

**Final design** — `src/scenes/panelTimeRangeCompare.tsx`, exporting `PanelTimeRangeCompare` (a `SceneTimeRangeCompare` subclass):
- **Per-panel scoping**: passed to `PanelBuilders.timeseries()...setHeaderActions(new PanelTimeRangeCompare())` on every timeseries panel, instead of the page's `controls` array. This works because `SceneQueryRunner.getClosestExtraQueryProviders()` walks **up** the scene graph from its parent and also checks each ancestor's **direct children** (`forEachChild`) for `ExtraQueryProvider`s, taking the *closest* match per type. `setHeaderActions()` registers its argument as a real child of the `VizPanel` (any `SceneObject`-typed state field is auto-discovered as a child by the generic `forEachChild` in `SceneObjectBase`), so an instance placed there scopes the compare toggle — and the shifted comparison query it adds — to that single panel, not the whole page.
- **Fixed option set**: `getCompareOptions()` is overridden (reassign `this.getCompareOptions` *after* `super()` in the subclass constructor — it's an instance-level arrow-function property, not a prototype method, so this cleanly shadows the base class's range-adaptive Day/Week/Month logic) to always offer **None / Hour before / Day before / Week before**, regardless of the panel's time range.
- **A real "None" option is mandatory**, not just the base class's implicit "cleared" state: with `hideCheckbox: true` (needed for the compact look), there's no separate checkbox to turn comparison off — clearing it has to be a selectable menu item. Its `value` must be the exact string `'__noPeriod'` that `SceneTimeRangeCompare`'s `onCompareWithChanged()` checks internally to call `onClearCompare()` — **not exported from `@grafana/scenes`**, inlined and verified against the installed package's compiled JS (a future scenes upgrade could silently break this).
- **Visual style**: inspected `play.grafana.org`'s actual "Predict CPU usage" button directly with Playwright (see gotcha below) rather than guessing — it's a plain `<Button variant="secondary" size="sm">`, no icon, no border at rest. Replaced the base class's default `ButtonGroup`+`ButtonSelect` renderer with a custom one: `static Component = PanelTimeRangeCompareRenderer` renders a `Button` (that exact variant/size) wrapped in a `Dropdown`+`Menu`, showing "Compare" at rest and the active option's label (e.g. "Week before") when a comparison is selected.

Demo-stack caveat: the local Prometheus only retains a small window of continuous data (it gets recreated/restarted across sessions), so Day-before/Week-before comparisons render no overlay line there — not a bug, just no data that far back yet. Verify against a real cluster's Prometheus/Thanos with real retention if this needs re-checking.

## Known gotchas discovered this/previous sessions (read before repeating work)

1. **Grafana's `renameByName` (in the `organize` transform) only sets a field's display name, never its underlying `field.name`.** Any custom cell renderer or code that looks up `frame.fields.find(f => f.name === X)` must use the pre-rename name, not whatever `renameByName` maps it to.
2. **`joinByField` is only safe when the join key is a single field that's actually unique across everything being combined.** When the natural identity is multi-field (Namespaces: cluster+namespace; Workloads: cluster+namespace+workload+workload_type), use Grafana's `{ id: 'merge', options: {} }` transform instead — it matches rows by every field name common to all queries in the pipeline, not one designated join key.
3. **Cross-page filter variable propagation.** `SceneAppPage`'s `$variables` are constructed eagerly for every top-level page at once. Each filter variable re-syncs its value from the raw URL query param **on activation**, never from the constructor, and is excluded from every top-level page's `preserveUrlKeys`. Do not reintroduce a constructor-time URL read, and do not add filter variable names back to `preserveUrlKeys`.
4. **`plugin.json` changes need a full Grafana container recreate**, not just a rebuild/restart. Pure code/panel changes only need `podman restart`.
5. **Webpack build cache goes stale** with the `node_modules`-symlink shortcut — `rm -rf node_modules/.cache/webpack` before trusting a build.
6. **Local demo containers (`kube-metrics-demo`, `prometheus`, `debeka-k8s-app` Grafana) bind-mount files from whatever worktree last recreated them, not necessarily this one.** `podman inspect <container> --format '{{range .Mounts}}...'` before assuming a container is serving *this* worktree's files. Recreate (not just restart) after repointing a bind mount to a different worktree's `dist/`/`demo/` paths.
7. **Adding a genuinely new npm dependency requires a real `npm install`, not the symlink trick** — and if the *shared* `node_modules` (from whatever worktree/branch it was last installed against) is missing a dependency your worktree's `package.json` declares (e.g. because that shared checkout is pinned to an older commit), don't `npm install` into the shared location — do a real, independent `npm ci`/`npm install` inside your own worktree instead, so you're not silently mutating a directory another worktree's build depends on.
8. **`joinByField` needs `mode: 'inner'`, not the default `'outer'`, when one of the joined queries is meant to act as an allow-list filter.**
9. **Grafana's built-in reducer/calc ids often already say exactly what's needed, verbatim** — `p95` → `"95th %"`, `lastNotNull` → `"Last *"`. Check `@grafana/data`'s `fieldReducer.mjs` for the exact id before inventing a custom label.
10. **A flexbox `SceneFlexItem` with `xSizing: 'fill'` plus `minWidth: 0` still won't guarantee equal-width siblings if one contains a long unbroken string** — set an explicit `width: '50%'` on both items instead of relying on flex distribution.
11. **This local Prometheus's `kube-metrics-demo` scrape job needs `honor_labels: true`.** Several demo metrics embed their own `job` label — without `honor_labels`, Prometheus overwrites it with the scrape job's own name, breaking `job="kube-state-metrics"` filters. Set in `demo/prometheus/prometheus.yml`.
12. **A `Nodes: Standalone plugin pages` Helm config option can hide specific app pages from the Grafana nav without touching plugin code** (`navigation.app_standalone_pages`). Nav-tree cosmetics only, not access control — the page is still reachable by direct URL. Needs a Grafana restart.
13. **Grafana Scenes' `SceneQueryRunner` discovers `ExtraQueryProvider`s (like `SceneTimeRangeCompare`) by walking *up* the scene graph from its parent, checking each ancestor and that ancestor's direct children** (`getClosestExtraQueryProviders`, `getClosest` + `forEachChild`), taking the closest match per constructor type. This means a provider doesn't have to live in a page's top-level `controls` — placing one as a `VizPanel`'s `headerActions` (any `SceneObject`-typed state field is auto-discovered as a scene-graph child) scopes it to that single panel. Useful pattern for any future "per-panel control" need, not just comparison.
14. **`SceneDataTransformer` interpolates scene variables into a transformation's `options`**, not just into query expressions — it `JSON.stringify`s the transformation config, runs `sceneGraph.interpolate` over the whole string, then `JSON.parse`s it back (`_interpolateVariablesInTransformationConfigs`). Confirmed by reading the compiled source, not just inferred: a `${var:regex}` token anywhere inside e.g. a `filterByValue` transform's `options` resolves correctly before the transform runs. A previous session had flagged this as unverified and left a row-filter unimplemented because of it — it works fine.
15. **Grafana's `match[]` HTTP parameter (used by `label_values(query, label)` template queries) only accepts a plain Prometheus series selector** — metric name + label matchers, not aggregations, `label_replace`, `OR`, or `group_left`. A complex query there fails with `invalid parameter "match[]": ... unexpected "("`. Use `query_result(<expr>)` instead (runs via a normal instant `/api/v1/query`, no such restriction) when the values you need only exist after PromQL processing (e.g. a label added by `label_replace`), paired with a `regex` field on the `QueryVariable` to pull the specific label back out of each result series' string form.
16. **Grafana's `query_result(...)` / `label_values(...)` wrapper-detection in template variable queries doesn't span newlines.** A multi-line, `#`-commented PromQL expression (the kind this codebase's larger queries are formatted as, for readability) passed to `query_result(...)` isn't recognized as the wrapper at all — Grafana falls through to sending the *entire literal string*, including the `query_result(` text, to the `match[]` endpoint, hitting the same failure as gotcha #15 above even though `query_result()` itself has no such restriction. Fix: strip `#`-comments and join every line with spaces into a single-line expression before wrapping it in `query_result(...)`.
17. **This project's checked-in code is *not* Prettier-formatted** — the committed style tolerates single-line object literals and PromQL template strings well past Prettier's default print-width (lines up to ~400 characters exist in `clustersApp.tsx`). Running `npx prettier --write` on a whole file you've touched will silently reformat large amounts of *unrelated, pre-existing* code into multi-line form, polluting the diff and making it impossible to cleanly split changes into per-feature commits afterward. **Don't run a blanket `prettier --write` on an edited file in this repo** — hand-format only the lines you actually changed, matching the surrounding file's existing (denser) style. (Bit this session: an end-of-session `git checkout HEAD -- <file>` + redo-the-edits-by-hand was needed to undo the pollution before committing.)
18. **Playwright's Chromium needs several system shared libraries (`libnspr4`, `libnss3`, `libatk*`, `libcups2`, etc.) that may not be installed, and `playwright install --with-deps` needs root.** If `sudo` isn't available (no password, no passwordless sudo), `apt-get download <package>` still works **without root** — it just downloads the `.deb` to the current directory. Extract with `dpkg-deb -x <file>.deb <dir>`, then run the browser with `LD_LIBRARY_PATH=<dir>/usr/lib/x86_64-linux-gnu` prepended. Got a fully working headless Chromium this way with zero root access — useful for any future session that needs to inspect a live external Grafana instance (like Grafana Play) or screenshot this app's own demo stack.

## Demo data (`demo/kube-metrics/metrics` + `demo/prometheus/prometheus.yml`)
Has: node info/capacity, per-node CPU/memory recording-rule-style aggregates, namespace-level CPU/memory recording-rule-style sums, a full set of storage metrics (PVC/PV/kubelet_volume_stats/container_fs_*), enriched `ALERTS`, and a small **Workloads demo set** in namespace `default` on both clusters: a Deployment "app", a DaemonSet "node-agent", a StatefulSet "cache", a completed Job "db-migrate", and a bare pod "debug-shell" (cluster-suffixed synthetic pod identities to avoid the multi-cluster pod-name collision described above).

- **Workloads' CPU Usage/CPU Requests % columns stay empty in the demo by design** — `node_namespace_pod_container:container_cpu_usage_seconds_total:sum_irate` deliberately has no pod-level rows added (would double-count into the Cluster CPU chart / Namespaces CPU Usage column, which already sum it at node granularity). Not a bug to "fix" unless also auditing every other consumer of that metric.
- `container_fs_{reads,writes}_total` counters are static, so `rate()` on them evaluates to 0 — Storage tab Throughput/IOPS panels showing flat 0 is expected.
- **The demo Prometheus only has a shallow, discontinuous data window** (it gets recreated across sessions along with the other demo containers) — day/week-before comparisons on the new per-panel compare feature won't show an overlay line until the container has been running continuously for that long. Verified directly via `curl .../api/v1/query --data-urlencode "query=up offset 1h"` returning empty results at the start of this session.

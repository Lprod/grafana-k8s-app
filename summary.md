# Session Summary — debeka-k8s-app (Grafana K8s Observability App Plugin)

**Repo:** https://github.com/Lprod/grafana-k8s-app (branch `main`)
**Current release:** `v1.2.1` on GitHub; this session's work is being released as **`v1.2.2`** (tag/release created right after this file was written — check GitHub if you need to confirm it landed).
**Reference design:** https://play.grafana.org/a/grafana-k8s-app/navigation/cluster/... ("Grafana Play") — this plugin is being rebuilt to visually/functionally match Grafana's own official Kubernetes Monitoring app, tab by tab. The user pastes the exact PromQL + panel titles from Grafana Play for each tab; translate `$cluster`/`$namespaces`/`$nodes` literally into this codebase's variable-interpolation style (see existing tabs for the pattern) rather than "fixing" them to look more consistent — the user has occasionally used different filter operators (`=` vs `=~`) or omitted a variable filter on purpose between panels, and that's preserved intentionally.

## Naming convention (use this when talking about pages)

- A top-level list page is named plainly: **Clusters**, **Nodes**, **Namespaces**, **Workloads**, **Alerts**.
- Its detail/drilldown page (reached by clicking a row) is named "**\<Name\> Drilldown**", e.g. **Clusters Drilldown**.
- This is also saved in persistent memory (`feedback_page_naming.md`).

## What exists today

### Clusters (list page) — `src/scenes/clustersApp.tsx: getClustersListScene`

Cluster column links to **Clusters Drilldown**; Nodes column links to **Nodes** page; Alerts column links to the **Alerts** page (`?var-cluster=<cluster>`, per-row, native table link). ### Clusters Drilldown — `getClusterDetailPage` in clustersApp.tsx
Tabbed page: **Overview, CPU, Memory, Network, Storage** (Logs/Events/Alerts tabs were deleted in an earlier session; "Network Storage" was split into two separate tabs). Title renders as "\<cluster-name\> [cluster]" badge via `ClusterPageTitle`. Datasource picker + timepicker in page-level controls.

- **Overview tab** (`getClusterOverviewScene`) — done:
  - Top row: "See Namespaces" / "See Workloads" buttons **+ `ClusterAlertsBadge`** (compact colored clickable pill, e.g. "3 firing alerts" — red if any critical, orange if warning-only, green if none; links to the Alerts page pre-filtered to this cluster). All three navigate via plain `Button`/`onClick={window.location.assign}`.
  - "Cluster information" heading → full-width **Cluster Health banner** (`ClusterHealthBanner`) → two **equal-width** `InfoCard` boxes (cluster info: name/nodes/provider; capacity: cpu/memory/disk). **Equal width needs an explicit `width: '50%'` on both wrapping `SceneFlexItem`s, not just `minWidth: 0`** — `minWidth: 0` alone lets a long unbroken value string (e.g. "demo-cluster-aws") force its box wider than its fair share even with equal flex-grow, because the string itself doesn't wrap. Fixed this session by (a) `width: '50%'` on both `SceneFlexItem`s (deterministic 50/50 split, not reliant on flex distribution) and (b) `wordBreak: 'break-word'` on `InfoCard`'s `.value`/`.valueLink` styles in `clusterOverviewCards.tsx` (defensive, in case a future value is long enough to overflow even a 50%-width box). **This is the second time this exact row has needed a width fix — if it looks uneven again, suspect new/longer content in one of the rows before re-deriving the flex fix from scratch.**
  - "Cluster optimization" heading → Cluster CPU / Cluster Memory timeseries (Capacity purple 14% fill / Limits red dashed / Requests orange dashed / Usage blue solid, Min/Mean/Max legend table).
  - "Nodes" heading → node/legend row → Nodes table.

### Alerts (top-level page) — `src/pages/Alerts/alertsPage.ts` + `investigateActionCell.tsx`
Kubernetes-icon + "Alerts" title, datasource picker + `cluster`/`node`/`namespace`/`severity`/`alertname` variable pickers + timepicker. 3 timeseries panels (Firing alerts by cluster/by namespace, Alert severity) + a table titled `Firing Alerts at ${__to:date:YYYY-MM-DD HH-mm-ss}` with columns CLUSTER/SEVERITY/ALERTNAME/NAMESPACE/POD/CONTAINER/ENDPOINT/INSTANCE/JOB plus a synthetic **Action** column. Severity column background colored via `overrideMappings` (info→blue, warning→yellow, critical→red, none→gray) — Grafana value mappings have no generic "else" for strings, so anything outside those four stays uncolored.

**"Investigate" button / Grafana Assistant integration** (`investigateActionCell.tsx`): each table row gets an `OpenAssistantButton` (official `@grafana/assistant` npm package, real dependency via `npm install`) that opens the Grafana Assistant sidebar with a per-row root-cause-analysis prompt + structured context. A custom `CustomTransformOperator` (`addActionField`) injects a synthetic `action` field since the alerts query has no natural field to hang a button on.

**The user's org runs a custom, in-house-forked assistant app** (https://github.com/elohmeier/grafana-pi-app, default plugin id `g42-pi-app`), not vanilla Grafana Cloud Assistant. It ships an alternate `grafana-assistant-app`-ID build meant to be a drop-in for the official `@grafana/assistant` SDK — **the user confirmed Debeka runs this variant**, so our `@grafana/assistant`-based implementation is the right approach and required **no changes on our side**. What it needed was two upstream fixes in `grafana-pi-app` itself, both found by us this session, both merged:

1. **PR [#30](https://github.com/elohmeier/grafana-pi-app/pull/30)** (merged, released in v2.18.1): `src/module.tsx`'s `ASSISTANT_SIDEBAR_TITLE` was hardcoded to `'Assistant'` even in the `grafana-assistant-app`-ID build, but `@grafana/assistant`'s `isAssistantAvailable()` requires an exact match against `'Grafana Assistant'` (in addition to the plugin id) — so `OpenAssistantButton` always resolved `isAvailable: false` and silently hid itself. Fix: make the title conditional on `pluginJson.id === ASSISTANT_PLUGIN_ID` (keeps `'Assistant'` for the default `g42-pi-app` build).
2. **PR [#31](https://github.com/elohmeier/grafana-pi-app/pull/31)** (merged): fixing #30 alone made the button *visible* but clicking it still did nothing. Root cause: a **second, independent** hardcoded `'Assistant'` string in `scripts/package-plugin-variant.mjs` (`sidebarTitle`, used to bake the *static* `extensions.addedComponents`/`addedLinks` declarations into the built `plugin.json` for the variant). Grafana core apparently consults this static manifest (not just the runtime-registered link) to resolve which component to render when the `OpenExtensionSidebarEvent` fires — so the still-mismatched manifest title meant no component was found, and the click was a silent no-op even though availability now correctly returned true. This likely also explains a reported missing "open Assistant" star icon on regular dashboards (driven by the same manifest entry). Fixed the same way: conditional on the variant's plugin id.

**If a future session hears "the Investigate button doesn't work" again**, check (in this order): (a) which plugin id is actually installed (`g42-pi-app` vs `grafana-assistant-app`), (b) whether the deployed `grafana-pi-app` version includes both of the above fixes (>= the release containing #31), (c) whether Grafana's `extensionSidebar` feature toggle is enabled (see below) — in that order, before assuming our plugin's code is broken.

**Local demo environment now runs the real `grafana-pi-app` build**, not the official Grafana Enterprise Assistant, specifically to make this reproducible:
- The Grafana Enterprise image ships the official assistant preinstalled at `/var/lib/grafana/plugins/grafana-assistant-app` (a normal external-plugin path) — bind-mount your own extracted build over that same path to replace it (`podman run ... -v <extracted-dir>:/var/lib/grafana/plugins/grafana-assistant-app ...`).
- It needs `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=debeka-k8s-app,grafana-assistant-app` (unsigned) and an app-provisioning entry to actually enable it (`/opt/debeka-k8s-app/provisioning/plugins/apps.yaml` now has a `grafana-assistant-app` entry alongside `debeka-k8s-app` — without this the plugin loads but stays `enabled: false`).
- **Grafana's `extensionSidebar` feature toggle must be enabled** (`GF_FEATURE_TOGGLES_ENABLE=extensionSidebar`, it's a `v0-alpha` extension point) or the whole sidebar mechanism is inert regardless of plugin correctness.
- The downloaded GitHub release zip includes prebuilt Go backend executables (`gpx_g42_pi_app_linux_amd64` etc, plugin.json has `"backend": true`) — a from-source `npm run build:variant` only produces the frontend `dist/`, no backend binary, and Grafana will fail the whole provisioning step ("plugin not installed") without one. Fastest way to test a frontend-only source change: patch the **already-working extracted release's** `plugin.json`/JS directly rather than rebuilding from source, if you just need to verify one small change.
- This local swap is a standing deviation from "official Assistant" and should probably stay in place for future sessions testing Assistant integration — check `podman inspect debeka-k8s-app` / the current `podman run` command in shell history if you need to know exactly what's mounted.

## Known gotchas discovered this session (read before repeating work)

1. **Cross-page filter variable propagation — the full, correct story (superseding every earlier, partial explanation of this in previous versions of this file).** `SceneAppPage`'s `$variables` are constructed **eagerly** (unlike the lazily-invoked `getScene` factory) for **every** top-level page at once, the instant `getClustersSceneApp()` runs — not just whichever page the user is navigating to. Since every top-level page (Clusters, Namespaces, Workloads, Nodes, Alerts) independently declares its own same-named `cluster`/`namespace`/etc variable, Scenes' URL-key deduplication (`UniqueUrlKeyMapper`) silently renames every page but the first-registered one to `-2`/`-3`/etc across the *whole* scene graph, and a cross-page link's plain `var-cluster=...` query param lands on a suffixed key nothing reads — the destination page shows "All". Fully fixed in `datasourceVariables.ts` with two changes, **both required together**:
   - Each filter variable re-syncs its value from the raw, unsuffixed URL query param **on activation** (`addActivationHandler` + `changeValueTo`), not from the constructor. Reading it in the constructor is actively harmful, not just insufficient: on a hard reload landing directly on a filtered page (e.g. `/alerts?var-cluster=X`), *every* top-level page's variable is constructed at that same instant and would *all* see that query param — including pages the user never visited — and that value then sits latent in memory and leaks back out the next time the user navigates to one of those other pages.
   - The filter variables were removed from every top-level page's `preserveUrlKeys` (kept only `from`/`to`/`timezone`/`refresh`/`var-datasource`). Scenes' own nav link generation (`getUrlWithAppState`) uses a page's declared `preserveUrlKeys` to decide what survives into links Scenes itself builds (sidebar, breadcrumbs) — with the filter keys included there, a stale filter value kept following the user around to unrelated pages even without our own activation-handler code being involved at all.
   - **Do not reintroduce a `value:`-based constructor read of the URL for these variables, and do not add filter variable names back to `preserveUrlKeys` — both were tried, both caused regressions, both are explained above.**
2. **`plugin.json` changes need a full Grafana container recreate**, not just a rebuild/restart, when nav entries change. Pure code/panel changes (no plugin.json diff) only need `podman restart`.
3. **Webpack build cache goes stale** when using the `node_modules`-symlink shortcut (`ln -s /opt/debeka-k8s-app/node_modules ./node_modules`) — always `rm -rf node_modules/.cache/webpack` before trusting a build. Remove the symlink when done.
4. **The `kube-metrics-demo` container's bind-mounted file goes stale on edit** — recreate, don't restart.
5. **`podman-compose` resolves the `kube-metrics-demo` bind-mount relative to the *current working directory*, not the worktree** — always recreate this container with an explicit manual `podman run -v <worktree-absolute-path>/demo/kube-metrics/metrics:...`, never via `podman compose` while working from a worktree.
6. **Panel-heavy pages need a long Playwright wait before screenshotting** — 10-15s for pages with 8-12+ concurrent panel queries or many variables to resolve first.
7. **Adding a genuinely new npm dependency requires a real `npm install`, not the symlink trick.**
8. **`joinByField` transform needs `mode: 'inner'`, not the default `'outer'`, when one of the joined queries is meant to act as an allow-list filter.**
9. **Grafana's built-in reducer/calc ids often already say exactly what's needed, verbatim** — `p95` → `"95th %"`, `lastNotNull` → `"Last *"`. Check `@grafana/data`'s `fieldReducer.mjs` for the exact id before inventing a custom label.
10. **A flexbox `SceneFlexItem` with `xSizing: 'fill'` (the default) plus `minWidth: 0` still won't guarantee two siblings render equal-width if one contains a long unbroken text string** (e.g. a cluster name) — the string itself doesn't wrap and can force its box wider even with correct flex-grow/min-width. For a genuinely deterministic equal split, set an explicit `width: '50%'` on both items rather than relying on flex distribution, and add `wordBreak: 'break-word'` to the text styles as a defensive backstop.
